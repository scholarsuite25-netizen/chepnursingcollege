## 1. EXECUTIVE MANDATE & AUDITOR CHARTER

### 1.1 Purpose
The **Global Enterprise Web Application Audit & Release Standard (GEWA-AS)** establishes an uncompromising, evidence-based verification protocol to evaluate any web application following the completion of its build phase and prior to live production deployment.

### 1.2 Core Audit Rules (Non-Negotiable)
1. **Evidence-Based Rule**: Never assume code is functional, secure, or production-ready because it compiles, passes linting, or was generated by an AI assistant. Every control must be verified through code inspection, static analysis, or safe reproducible execution.
2. **Audit First, Refactor Later**: The auditor must conduct a complete discovery and risk assessment before making modifications, updating dependencies, or altering runtime behavior.
3. **Zero Destructive Actions**: Never execute destructive database queries, drop tables, invoke live payment gateways with real funds, send unmocked mass SMS/emails, or trigger live attack traffic against third parties.
4. **Credential & PII Redaction**: Under no circumstances may real API secrets, database passwords, session tokens, private keys, or personally identifiable information (PII) be committed to logs, reports, or test fixtures.
5. **No Synthetic Passes**: An unavailable scanner, an unconfigured test runner, or an unexecuted test suite must be explicitly reported as **NOT ASSESSED** or **BLOCKED**—never as a pass.
6. **Release Veto Authority**: The audit team holds binding release gating authority. If a **Critical** or **High** severity vulnerability remains unresolved, deployment to production is automatically blocked.

## 2. FULL-LIFECYCLE SDLC INTEGRATION FRAMEWORK

While traditional security audits only inspect code at the end of development, this standard integrates the entire **Software Development Life Cycle (SDLC)** to eliminate architectural drift and technical debt.

```
+---------------------------------------------------------------------------------------------------+
|                                     SDLC GOVERNANCE GATES                                         |
+---------------------+---------------------+---------------------+---------------------------------+
| Gate 1: Design      | Gate 2: Code Quality| Gate 3: QA & Tests  | Gate 4: Release & Post-Launch   |
| • Architecture RTM  | • Clean Code / Type | • Unit Tests        | • CI/CD Automated Pipeline      |
| • Threat Modeling   | • Dependency Scans  | • Integration Tests | • Go/No-Go Checklist            |
| • Data Classification|• Branch Policies   | • E2E Journeys      | • Rollback & Disaster Recovery  |
+---------------------+---------------------+---------------------+---------------------------------+
```

### 2.1 Requirements Traceability Matrix (RTM)
The audit verifies that:
- Every business requirement maps to concrete routes, components, and backend handlers.
- Orphaned features (code built without business requirement) are identified to prevent attack surface expansion.
- Incomplete user journeys (e.g., student submits admission but fee confirmation fails silently) are flagged as functional release blockers.

### 2.2 Shift-Left Architecture & Code Quality
- **Static Typing Strictness**: TypeScript/compiler flags must enforce strict null checks (`strict: true`), disallowing unsafe `any` casts or unchecked boundary conversions.
- **Modularity & Separation of Concerns**: UI presentation, application business logic, and database persistence layers must remain strictly decoupled.
- **Technical Debt & Legacy Artifacts**: Scratchpad scripts, deprecated endpoints, mock bypasses, and temporary test fixtures must be removed from production bundles.

### 2.3 Change Management & Branching Hygiene
- Enforcement of protected `main`/`production` branch rules.
- Mandatory peer-review pull requests with automated continuous integration (CI) status checks passing prior to merge.
- Semantic versioning (SemVer) tagging with audit changelogs.

## 3. DEVOPS & DEVSECOPS ENGINEERING SPECIFICATION

This section defines the operational DevOps and DevSecOps requirements necessary for resilient cloud deployment.

### 3.1 Continuous Integration & Automated Pipelines (CI/CD)
The application must maintain an automated CI pipeline (e.g., GitHub Actions, GitLab CI, AWS CodePipeline) that executes on every push and pull request:
1. **Dependency Installation**: Deterministic lockfile verification (`npm ci`, `poetry install --frozen-lockfile`, `bundle install --deployment`).
2. **Static Application Security Testing (SAST)**: Automated scanning for syntax, AST vulnerabilities, and dangerous function invocations.
3. **Software Composition Analysis (SCA)**: Automated dependency vulnerability scans (`npm audit --audit-level=high`, `snyk`, `trivy`) to block known CVEs.
4. **Secret Scanning**: Pre-commit and pipeline scanners (`gitleaks`, `trufflehog`) detecting committed tokens, API keys, and connection strings.
5. **Static Type Checking & Linting**: Execution of compiler checks (`tsc --noEmit`, `eslint`, `flake8`) with 0 errors required.
6. **Automated Test Pyramid**: Synchronous execution of unit, integration, and contract tests.
7. **Production Build Gate**: Zero-error generation of production distribution bundles.

### 3.2 Infrastructure, Runtime & Environment Isolation
- **Environment Parity**: Complete separation of Development, Staging, and Production environments. Secrets and database instances must never be shared between environments.
- **Runtime Compatibility**: Explicit verification of Node.js, Python, or container runtime versions against cloud platform limits (Vercel, AWS Lambda, Kubernetes, Docker, Cloudflare Workers).
- **Filesystem Constraints**: In serverless environments, code must not write to local disks expecting persistence. All uploads, assets, and session state must target cloud object storage (S3, Cloudflare R2, Supabase Storage).

### 3.3 Site Reliability Engineering (SRE), Observability & Health Checks
- **Health Check Specification**: Every application must expose authenticated or public lightweight health endpoints:
  - `/api/health` or `/healthz`: General application liveness check.
  - `/api/ready` or `/readyz`: Database and downstream integration readiness check.
- **Structured Telemetry & Logging**: Application logs must output structured JSON containing timestamp, severity (`INFO`, `WARN`, `ERROR`), request ID, route, and execution time without leaking user PII.
- **Application Performance Monitoring (APM)**: Integration with APM and error-tracking systems (Sentry, Datadog, OpenTelemetry) to alert on unhandled exceptions and performance spikes.

### 3.4 Disaster Recovery & Zero-Downtime Deployment
- **Rollback Readiness**: The deployment platform must support immediate, one-click atomic rollbacks to the prior healthy release bundle.
- **Database Backup & Migration Safety**: Database schema updates must be backward-compatible (expand-and-contract pattern) to prevent breaking currently running instances during rollouts. Automated daily point-in-time recovery (PITR) backups must be validated.

## 4. THE 10-PHASE EVIDENCE-BASED AUDIT PROTOCOL

Every audit executed under GEWA-AS must systematically evaluate all 10 phases below:

### Phase 1: Project Discovery, Architecture & Inventory
1. Identify framework runtime, major version, package manager, and lockfile consistency.
2. Map architecture: Monolith vs Microservices vs Serverless / App Router vs Pages Router.
3. Inventory all public and private routes, pages, forms, endpoints, and server actions.
4. Inventory all external services (Database, Auth provider, Payment gateway, Cloud Storage, AI APIs).
5. Audit environment variable declarations: verify `.env.example` exists without exposed secrets.

### Phase 2: Authentication, Session & Identity Security
1. Verify password hashing algorithms (Argon2id, bcrypt; never SHA1 or MD5).
2. Audit session lifecycle: creation, token expiration, renewal, revocation, and invalidation upon logout.
3. Verify cookie security attributes: `Secure`, `HttpOnly`, `SameSite=Lax` or `Strict`, proper domain scope.
4. Test for account enumeration via timing discrepancies or distinct error messages on login/password-reset.
5. Check brute-force defense: rate limiting, CAPTCHA, or progressive delay on authentication endpoints.
6. Inspect OAuth/OIDC implementations for `state` parameter validation and PKCE (Proof Key for Code Exchange).
7. Eliminate all mock authentication bypasses, default credentials, and backdoor accounts.

### Phase 3: Authorization, RBAC, Multi-Tenancy & Access Control
1. Construct an **Access-Control Matrix** for every route, API endpoint, and Server Action:
   - Audience: Public, Authenticated User, Student, Faculty, Admin, Super-Admin.
   - Enforcement location: Middleware vs Server-side route handler vs Database RLS.
2. Test for Insecure Direct Object References (IDOR/BOLA): Can User A access or mutate User B's profile, grades, invoices, or records by manipulating IDs in URLs or request payloads?
3. Test for Privilege Escalation: Can an unprivileged user assign themselves elevated roles via parameter tampering (e.g., `role: "admin"` in JSON body)?
4. Verify Tenant Isolation: In multi-tenant systems, ensure database queries enforce tenant keys (`organization_id`, `school_id`) on both reads and writes.
5. **Critical Next.js / Modern Rule**: Never rely solely on client-side navigation guards or hidden buttons for authorization. Server handlers must independently enforce permissions.

### Phase 4: Input Handling, Injection Defense & OWASP Top 10
1. **SQL / NoSQL Injection**: Verify all database queries use parameterized prepared statements or trusted ORM methods. Zero string concatenation in query construction.
2. **Cross-Site Scripting (XSS)**: Inspect HTML rendering for unsafe APIs (`dangerouslySetInnerHTML`, `v-html`, `innerHTML`). Verify contextual output encoding.
3. **Cross-Site Request Forgery (CSRF)**: For cookie-authenticated sessions, verify anti-CSRF tokens or `SameSite` cookie protections across all state-mutating requests (POST, PUT, DELETE, PATCH).
4. **Server-Side Request Forgery (SSRF)**: Inspect user-supplied URLs used in server-side fetches. Verify IP allowlisting/denylisting (blocking internal private IPs: `127.0.0.1`, `169.254.169.254`, `10.0.0.0/8`).
5. **File Upload Security**: Validate MIME types via magic bytes (not file extensions), enforce maximum file size limits, sanitize filenames to prevent path traversal (`../`), and store files outside public web roots.
6. **Open Redirects**: Verify redirection parameters (`?returnUrl=`, `?redirect=`) against strict internal path allowlists.

### Phase 5: Framework-Specific Boundaries & Client/Server Isolation
1. **Next.js App Router & React 19 Boundaries**:
   - Verify `"use client"` vs `"use server"` boundaries.
   - Ensure Server Actions are not exposing sensitive server-only business logic or raw database access to the public client bundle.
   - Verify sensitive internal packages or helper functions import `server-only` to prevent accidental bundling into client JavaScript.
2. **Data Serialization & Leakage**: Inspect data passed from Server Components to Client Components. Verify that unneeded database columns (password hashes, private keys, internal tokens) are stripped before serialization.
3. **Cache Isolation**: Ensure dynamic, user-specific data is not cached globally across user sessions (`revalidatePath`, `revalidateTag`, `cache: 'no-store'`).
4. **Environment Exposure**: Verify that only variables explicitly intended for the browser use `NEXT_PUBLIC_*` (or `VITE_*`). Ensure database connection strings and service role keys NEVER carry public prefixes.

### Phase 6: API Services, Server Actions & Integration Contracts
1. Audit all REST/GraphQL endpoints and Server Actions for input schema validation (Zod, Yup, Joi, Pydantic).
2. Enforce payload size limits to prevent Denial of Service via oversized JSON or multipart payloads.
3. Enforce rate limiting across sensitive and public endpoints.
4. Verify external integration failure modes: circuit breakers, timeouts, and exponential backoff for third-party APIs (Remita, Paystack, Stripe, OpenAI/Gemini, Twilio).
5. Validate webhook handlers: cryptographic signature verification (HMAC SHA-256), replay protection via timestamp checks, and idempotent processing.

### Phase 7: Database Architecture, Migrations & Data Integrity
1. Schema normalization: verify primary keys, foreign key constraints, cascading deletes, and nullability.
2. Unique constraints: ensure duplicate submissions cannot create conflicting records (e.g., matriculation numbers, email addresses, transaction references).
3. Indexes: verify database indexes cover frequent filter, sort, and join columns (`user_id`, `created_at`, `status`).
4. ACID Transactions: ensure multi-step business operations (e.g., student payment + course registration) execute inside database transactions with rollback on failure.
5. Row-Level Security (RLS): in Supabase/PostgreSQL, verify that RLS is enabled on all tables with explicit policies for SELECT, INSERT, UPDATE, and DELETE.

### Phase 8: Performance, Core Web Vitals, Reliability & Concurrency
1. **JavaScript Bundle Size**: Identify bloated client libraries (e.g., full lodash, moment.js) and recommend tree-shaking or lightweight alternatives.
2. **Core Web Vitals**:
   - Largest Contentful Paint (LCP) < 2.5s.
   - Cumulative Layout Shift (CLS) < 0.1 (explicit image dimensions, font preloading).
   - Interaction to Next Paint (INP) < 200ms.
3. **Asset & Image Optimization**: Verify responsive images (`next/image`, WebP/AVIF formats), font optimization, and CDN caching headers.
4. **N+1 Query Detection**: Audit data fetching loops to ensure queries are batched or joined.
5. **Concurrency & Race Conditions**: Verify critical state mutations (seat booking, exam submission, wallet debits) use atomic updates or optimistic locking.

### Phase 9: Multi-Tier Testing Pyramid Execution
1. **Unit Tests**: Test pure business logic, fee calculations, validation rules, utility functions, and edge cases (boundary values, null, NaN).
2. **Component Tests**: Test UI rendering, empty states, error banners, accessibility keyboard navigation, and form validation triggers.
3. **Integration Tests**: Test Server Actions and API endpoints against isolated test databases or mock adapters.
4. **End-to-End (E2E) Tests**: Execute automated browser flows (Playwright/Cypress) for core user journeys:
   - Candidate application -> Fee payment -> Screening slip generation.
   - Student login -> Exam/CBT session -> Submission -> Result logging.
   - Admin login -> Student record approval -> Portal dispatches.
5. **Security Regression Tests**: Automated tests asserting that unauthenticated or unauthorized requests are rejected with HTTP 401/403.

### Phase 10: DevOps CI/CD, Infrastructure & Deployment Readiness
1. **Security Headers**: Verify HTTP response headers via helmet/middleware:
   - `Content-Security-Policy` (CSP)
   - `X-Frame-Options: DENY` or `SAMEORIGIN`
   - `X-Content-Type-Options: nosniff`
   - `Strict-Transport-Security: max-age=63072000; includeSubDomains; preload`
   - `Referrer-Policy: strict-origin-when-cross-origin`
   - `Permissions-Policy: camera=(), microphone=(), geolocation=()`
2. **Build Smoke Test**: Execute clean production build (`npm run build`) in a pristine environment and confirm 0 errors.
3. **Local Production Smoke Test**: Run production server (`next start` / production container) and verify key routes return HTTP 200 without runtime hydration errors.
4. **Deployment Gate Review**: Complete the itemized Go/No-Go release checklist.

## 5. STANDARDIZED AUDIT DELIVERABLES & SCHEMAS

Every audit executed under this standard must output five standardized artifacts:

### Deliverable 1: PRE_DEPLOYMENT_AUDIT.md
Master technical report containing:
- Executive Summary & Scope Overview
- Application Architecture & Trust Boundaries
- Detailed Findings by Category & Severity
- Complete Access-Control Matrix
- Remediation Plan (P0: Blockers, P1: High Priority, P2: Improvements)
- Final Release Verdict:
  - **READY**: Zero Critical/High issues, all critical journeys tested.
  - **CONDITIONALLY READY**: Low/Informational items only, waivers approved.
  - **NOT READY**: Confirmed Critical/High vulnerabilities or broken flows present.

### Deliverable 2: AUDIT_FINDINGS.csv
Machine-readable spreadsheet formatted with the following columns:
```csv
Finding_ID,Category,Severity,Confidence,File_Path,Line_Number,Vulnerability_Title,Impact_Description,Root_Cause,Remediation_Recommendation,Release_Blocker
SEC-001,Authentication,Critical,Confirmed,src/app/actions/auth.ts,42,Missing Password Hashing,Plaintext password stored,Direct assignment without bcrypt,Implement bcrypt.hash with cost 12,YES
SEC-002,Authorization,High,Confirmed,src/app/actions/admin.ts,18,Missing Server-Side Role Check,Unauthenticated admin mutation,Trusting client UI check,Verify session role in server action,YES
```

### Deliverable 3: TEST_PLAN.md
Structured test specification containing:
- Test Strategy & Scope
- Risk-Based Test Matrix (Test ID, Level, Feature, Preconditions, Inputs, Expected Output, Priority)
- Environment Isolation & Mocking Strategy

### Deliverable 4: TEST_EXECUTION_REPORT.md
Concrete execution evidence containing:
- Exact commands executed and terminal exit codes
- Summary table: Tests Passed, Failed, Skipped, and Blocked
- Measured test code coverage (Statements, Branches, Functions, Lines)
- Reproduction logs for any observed test failures

### Deliverable 5: DEPLOYMENT_CHECKLIST.md
Structured release checklist where every item is classified as `PASS`, `FAIL`, `NOT VERIFIED`, or `NOT APPLICABLE`:
```markdown
| Gate Item | Category | Verification Method | Status | Notes |
|:---|:---|:---|:---:|:---|
| 01. TypeScript Compilation | Build | `npx tsc --noEmit` | PASS | 0 type errors |
| 02. ESLint Code Quality | Code | `npm run lint` | PASS | Clean |
| 03. Production Build | Build | `npm run build` | PASS | 22 routes generated |
| 04. No Exposed Secrets | Security | Git & Env Audit | PASS | All keys in env |
| 05. Health Check Endpoint | DevOps | GET /api/health | PASS | Returns 200 OK |
| 06. HTTPS & Security Headers | Infra | Curl inspection | PASS | HSTS & CSP active |
```
